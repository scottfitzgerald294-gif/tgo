# 拼多多客服架构决策记录

## 1. 决策总览

| ADR | 决策 | 状态 |
|---|---|---|
| ADR-001 | 以 TGO 作为客服与 AI 底座 | 已接受 |
| ADR-002 | 使用独立 PDD Connector | 已接受 |
| ADR-003 | 使用 RAG 而不是模型微调 | 已接受 |

这些决策适用于第一版范围：文本消息、标准化、去重、RAG、回答校验、风险规则、人工转接、回复互斥和审计。交易写操作、多模态自动处理和未经官方确认的 PDD 协议不在第一版内。

## ADR-001：以 TGO 作为客服与 AI 底座

### 背景

项目需要访客、会话、客服分配、等待队列、实时消息、AI Agent、知识检索、人工接入和浏览器工作台。当前 TGO 已提供：

- `tgo-api` 的 Project、Platform、Visitor、Session、Staff、Queue 和权限。
- WuKongIM 实时频道和消息。
- `tgo-ai` 的 Agent、模型、工具和会话记忆。
- `tgo-rag` 的 Collection、QA、文件、Embedding 和混合检索。
- `tgo-web` 的人工接入、AI 开关、转接、结束和消息发送。
- `tgo-platform` 的渠道 Listener、Inbox、Adapter 和 custom 出站回调。

### 决策

复用 TGO 作为通用客服和 AI 底座，只在外部增加 PDD Connector 和安全控制，不重建第二套客服系统。

### 理由

- 已有完整人工服务生命周期，避免重复实现高竞态业务。
- 已有 Project 范围和权限基础。
- 已有浏览器实时工作台。
- 已有 Agent 与 RAG 绑定，适合商品和政策知识。
- 渠道边界和核心业务可以分离。

### 后果

正面：

- 第一版工作集中在连接器和安全边界。
- 其他渠道能力与 PDD 可以共享人工、AI 和知识体系。
- 上游持续改进可被复用。

代价：

- 必须适配 TGO 当前“先建立客服 Session，再判断 AI”的流程。
- WuKongIM 内部消息和 PDD 外部送达必须建立明确状态区别。
- 上游 API 变化需要契约测试保护。

### 未选择方案

- 从零自建客服平台：重复建设会话、权限、工作台、实时消息和人工分配，风险和周期更高。
- 只做无工作台机器人：无法满足默认转人工、人工接管和审计要求。

## ADR-002：使用独立 PDD Connector

### 背景

拼多多协议、凭据、回调验证、幂等和外部送达属于平台专有边界。仓库当前没有 PDD 实现，`channel_integration` 只有能力声明，没有可直接承载持久 Inbox 和完整渠道生命周期的通用宿主。

### 决策

PDD 适配器作为独立服务部署，未来代码位于 `extensions/pdd-connector/`。它是 PDD 入站与出站的唯一入口。

### 理由

- PDD 凭据可以限制在最小信任域。
- 协议升级不需要修改 TGO 通用核心。
- Connector 可拥有独立 Inbox、Outbox、审计和回复租约。
- 可单独扩缩容、限流、暂停和回滚。
- 可以在不影响 TGO 其他渠道时停止 PDD 自动化。

### 后果

正面：

- 安全边界清晰。
- 上游合并冲突少。
- PDD 协议测试可以使用官方夹具独立验证。

代价：

- 增加一个服务和一个自有数据 schema。
- 需要维护 TGO HTTP/SSE 契约。
- 必须防止任何绕过 Connector 的 PDD 出站路径。

### 未选择方案

- 直接把 PDD 代码写入 `repos/tgo-platform`：升级冲突和凭据暴露范围更大。
- 只使用 UI 插件：无法可靠承载公网回调、持久 Inbox 和 Outbox。
- 在每台客服电脑运行连接器：凭据分散，无法保证统一幂等和回复互斥。

## ADR-003：使用 RAG 而不是模型微调

### 背景

商品说明、店铺政策和 FAQ 会频繁变化，需要可追踪来源、按 Project 隔离和快速撤回。模型微调不适合承载实时事实，也不天然提供来源证据。

### 决策

第一版使用 TGO RAG Collection 和 Agent 绑定，不进行模型微调。

### 理由

- 知识可以按 Project 和 Collection 隔离。
- 文档可版本化、审核、删除和重新索引。
- 检索结果具有文档 ID、相关度和来源，可供 Guard 审核。
- 知识更新不需要训练和发布新模型。
- 无证据时可以确定性转人工。

### 后果

正面：

- 回答可追溯。
- 店铺知识更新速度快。
- 降低把其他租户知识固化进模型的风险。

代价：

- 需要高质量切分、Embedding、阈值和知识治理。
- 检索失败会降低自动回复覆盖率。
- RAG 证据不能自动保证答案正确，仍需要回答校验。

### 未选择方案

- 模型微调：成本高、更新慢、难删除单条知识、缺少天然引用。
- 把全部知识写入 Prompt：上下文过长、版本难管、容易跨租户混入。
- 直接让模型使用常识回答：无法满足证据和审计要求。

## ADR-004：不确定时默认转人工

### 背景

客服回答可能影响交易、赔付、个人数据和消费者权益。模型、RAG、网络或协议任何一层都可能失败。扩大自动回复覆盖率不能优先于避免错误承诺和双重回复。

### 决策

Guard 只有在证据充分、低风险、租约有效和所有依赖正常时批准自动回复；其他情况全部转人工并禁用 AI。

### 理由

- 对高风险错误采用 fail-closed。
- 复用 TGO 已有分配、排队和人工接管。
- 规则异常不会静默放宽。
- 可逐步按已验证意图扩大自动范围。

### 后果

正面：

- 明确限制模型幻觉和协议异常的外部影响。
- 人工始终拥有最高回复优先级。
- 事故时可按店铺关闭自动回复。

代价：

- 第一版自动回复率较低。
- 需要足够人工容量和队列监控。
- Guard 阈值过严会增加等待时间。

### 未选择方案

- 默认自动回复、出错再纠正：错误承诺可能不可逆。
- 仅依赖模型自报置信度：模型置信表达不等于事实可靠性。
- 仅靠 Prompt 要求“谨慎”：不能原子控制外部发送。

## ADR-005：使用浏览器工作台，而不是每台电脑本地运行 AI

### 背景

TGO Web 已支持会话列表、WuKongIM 实时消息、人工接入、AI 开关、转接和结束。若每台客服电脑本地运行 AI 或 Connector，会产生版本、密钥、审计、资源和回复一致性问题。

### 决策

客服统一使用服务端部署的 `tgo-web` 浏览器工作台。模型、RAG、PDD Connector、凭据和回复租约都运行在服务端。

### 理由

- 客服电脑不保存 PDD 或模型密钥。
- 模型和策略只有一个受控版本。
- AI/人工租约在服务端原子执行。
- 运维、升级、审计和事故停用集中管理。
- 低配置终端也能使用。

### 后果

正面：

- 终端攻击面和维护成本更低。
- 所有客服行为进入统一权限和审计。
- 无需为每台电脑分配 GPU 或模型环境。

代价：

- 依赖服务端和网络可用性。
- 需要浏览器会话安全、短期 Token 和合理超时。
- 高峰模型和 RAG 资源需集中扩容。

### 未选择方案

- 每台电脑本地运行模型：难统一版本、知识、策略和审计。
- 每台电脑保存 PDD 凭据：泄漏面过大，无法集中轮换。
- 原生桌面客户端作为第一版：重复现有 Web 能力并增加发布链。

## 2. 决策约束

以上决策共同产生以下不可破坏约束：

- 没有官方 PDD 资料和授权测试条件时，不启用协议实现或自动收发。
- 所有 PDD 出站必须经过 Connector Outbox 和 reply lease。
- TGO 的 AI 消息不自动等价于 PDD 已送达。
- RAG 无证据时不自动回复。
- 人工可以随时抢占 AI，旧 epoch 的候选永不发送。
- 客服浏览器不持有平台和模型密钥。
- 需要核心修改时使用独立、可回退、可上游合并的最小提交。
